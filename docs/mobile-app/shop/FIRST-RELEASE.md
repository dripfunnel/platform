## 1. Decisions

| Decision | Rejected | Why |
|---|---|---|
| **Native, in a fixed layout, branded with the store's logo, colours and font**, on the Shop API (decided 2026-10-22; the API serves the name and logo today, the colours and font are not served yet: shop/ARCHITECTURE.md §4) | The storefront website in a web view | Apple rejects apps that only wrap a website (4.2), and checkout in a web view is fragile. The AI-designed theme is website code a native app can't run, so the app looks like the store's brand, not like its website. |
| **The storefront's rules hold** (storefront/DESIGN.md, AGENTS.md "Storefronts"): no invented data; the price with its tax label, legal and compliance notices and the order summary at review are always shown as the Shop API gives them, but not the "Powered by" line (below) *(proposed)*. The Shop API serves whether prices include tax (`store.pricesIncludeTax`) and stock as `inStock` and `available`, not sentences, so the app words the tax line and the stock line from messages, chosen by those values and never computed (decided on #861) | App-only rules | The same store, the same customers, the same law. |
| **Customers sign in the way the store chose** (Settings › Customer accounts; ACCESS.md §2.1), and their account is the one they have on the website *(proposed)* | A separate app account | Customer accounts are per store already (USERS-AND-DOMAINS §1); the app is one more door to the same account. |
| **Every payment method the store offers on the website, through each provider's native SDK**: Stripe (Payment Sheet), PayPal, Razorpay, Cashfree and PhonePe, plus cash on delivery and bank transfer (decided 2026-10-22) | A web checkout page inside the app | The payment element is sealed on the website; in the app the provider's own sheet plays that part. Physical goods must not use in-app purchase (Apple 3.1.3(e)). |
| **No "Powered by" line in the store's apps**, shop or delivery (decided 2026-10-22) | The line in Account, following the plan, as on the website | The apps carry only the store's brand, published under the merchant's name. The website's sealed line is unchanged. |
| **No offline cart or checkout**: browsing shows the last loaded page with a banner; writes need a connection *(proposed)* | An offline queue | As the merchant app (merchant/ARCHITECTURE.md §5). |

## 2. What the release contains

| Area | Contains |
|---|---|
| **Getting in** | Browse without signing in. Sign in, register and reset by the store's methods (email and password, mobile code, or both); register and reset are by the six-digit code the API emails or texts, which proves the address and sets the password (ACCESS.md §2.1), not by a link. Delete my account in Account (Apple 5.1.1(v)): **not built on #862**, because the Shop API has no operation for it; it needs its own card for the API and the screen, and the app cannot go to the App Store without it |
| **Home** | The store's collections and products as the Shop API offers them, the announcement, search |
| **Browse** | Collections with the store's filters and sorting, search, product (photos, video, options and versions, price with tax label, stock as the API words it, the store's product sections) |
| **Cart** | Lines, quantities, offer codes (OFFERS-DESIGN rules, worded by the code's state), the totals the engine prices; a line the engine cannot sell (gone, short, not sold here) is said and blocks checkout until it is fixed |
| **Checkout** | Contact, address with a **map pin** (asked always, so own delivery can decide; api/DELIVERY.md §2), the delivery option the address gets, payment, review with the order summary, confirmation. **Built on #863 for cash on delivery and bank transfer, on #864 for Stripe and PayPal and on #865 for Razorpay, Cashfree and PhonePe**: every method the store offers is listed in the API's order; a provider the app does not take (none of today's) is greyed with "not available in the app yet", so `placeOrder` is never called for a provider the app cannot complete. **Stripe, PayPal, Razorpay, Cashfree and PhonePe** place the order with the app's scheme (and Stripe's SDK API version), then open the provider's own sheet (Stripe's Payment Sheet, Razorpay's, Cashfree's and PhonePe's native checkouts, each set up only from the API's answer; PayPal's approval page in the in-app browser) and read the order until the provider's webhook marks it paid, a short poll with a limit (every 2 seconds for 30): the app never marks an order paid. A closed, declined or failed sheet comes back with its reason and **retries the same way on the same order** (`payOrder`, a new attempt, never a second order): the prototype's "or choose another way to pay" is not built, since a placed order cannot change its way to pay (decided on #864; it needs an API operation of its own). A payment still unconfirmed at the limit says so, offers no second payment, and the shopper can check again. Only a payment the API reports as `paid` counts as paid (an `authorised` one is still unconfirmed), and an order the API reports as cancelled says so and offers no new attempt, since `payOrder` would refuse it. Google Pay shows where the device and the account allow it; Apple Pay only for a store whose file names `APPLE_PAY_MERCHANT_ID` (README §3). Razorpay's and Cashfree's checkouts offer UPI, cards and netbanking themselves, and PhonePe's opens the PhonePe app; the app only names the UPI apps they may open (ARCHITECTURE §3), and Cashfree's missing mobile number is the API's `PHONE_REQUIRED`, which sends the shopper back to Contact. None of the three SDKs runs in Expo Go: a build without them says "We couldn't start the payment", and every other screen works. A shopper who closes a Razorpay or PhonePe checkout is told they closed it; Cashfree does not document how it names that, so a closed Cashfree checkout may be worded as declined. The review's legal notice is the prototype's sentence ("By placing your order you agree to our Terms and Returns policy…") as plain words: the Shop API serves no policy text or links, and the three names become links with the Legal pages (SH 14). Not built, drawn in the prototype: marketing consent, billing address, copy bank details and the notifications prompt (designs/MISSING-FEATURES.md §5) |
| **Orders** | **Built on #866.** A signed-in customer's list (Account → Orders, a page of 20 at a time) and an order: its lines, totals as the API worked them out, payment and delivery method, the status in words (cancelled, where its delivery is, or how its payment stands), and for an own delivery where it stands and a button to follow it. A guest has no list (it asks them to sign in); their order opens from its confirmation ("View order") or a push, read by the cart token that placed it, which the phone keeps for that order, since the next cart's token replaces it, for 30 days and for the 20 newest orders (it reads the order, so it does not outlive them). **Tracking** (`orders/[id]/track`) for own delivery: the steps with their times in the store's time zone, named; while a rider is assigned or has the parcel, the rider's first name, photo, vehicle and a Call to their number, and the **handover code** large and readable ("Give this code to your rider"); while the parcel is on the way, the live map with the rider's position, the arrival time and when the position was reported. It asks again every 15 seconds only while the screen is in view and the app in the foreground, stops once the delivery has ended, asks at once on coming back, and keeps the code and the position on no disk and in no log. Each field shows only in the states it belongs to, whatever a late answer still carries. **Not built, because the Shop API does not give it** (decided on #866; each is a card for the API): the delivery address and its pin (so the live map shows the rider alone, with no address pin, and an order has no "Deliver to" line), a courier's name, tracking number and link (so a courier order shows its state and shipping method, with no "Track with" button), bank-transfer instructions after placement, and cancel and return |
| **Account** | Profile, addresses (with pins), sign out, delete account |
| **Notifications** | Order placed, rider assigned, on the way, delivered, not delivered, courier shipped (api/DELIVERY.md §6). **Built on #866 for the customer's rider assigned, on the way, delivered and not delivered** (the pushes the API sends today): after the first order, never at launch, one offer in the store's name says what a notification holds (never the code, an address or an amount); a customer's phone is registered for every order and a guest's for the order, with the token kept for it; a tapped push opens that order's tracking; sign-out removes the phone first (with no signal it tries twice, and the phone stays registered to that customer until its next registration moves it: ending a session should drop its devices on the server, a card for the API). **Only for a store whose file names `EAS_PROJECT_ID`** (README §3): without it the app never asks and registers nothing. Remote push cannot run in Expo Go on Android, only in a development or store build |
| **Markets** | The store's languages and currencies, chosen as on the website |
| **Legal** | The store's legal pages, opened in the in-app browser from the storefront *(proposed)* |

Not in the first release: wish lists, reviews, the journal, the store's content pages beyond
legal ones, and any theme section the AI built on the website.

## 3. Design

`designs/DF Shop App Prototype.dc.html` (#854) draws every screen above at phone width with its
empty, loading, error and offline states, for an India and a US sample store, and `designs/design.md`
maps it. It also draws a few things this release does not contain; they are listed in
`designs/MISSING-FEATURES.md` §5 and are not built unless this document adds them. The prototype
decides behaviour and wording; this document decides scope (docs/README.md §3).
