# docs/ui: the browser apps (`apps/ui/`)

How every SPA in `apps/ui/` is built: the stack, the folder structure, the conventions for
routes, screens, API calls, text, navigation and states, and how to add a screen. Each app's
own guide says what that app is for, who uses it and what it may do.

**Status: skeleton.** Each app has a sign-in route and a home route; `shared/` has a button,
design tokens, the GraphQL client and money formatting.

Last updated: 2026-09-28.

| App | Guide | Host | Users | API | Look |
|---|---|---|---|---|---|
| `apps/ui/store` | [store/](store/README.md) | each partner's portal host, e.g. `store.<partnerdomain>` | Merchants (Owner, Manager, Staff) and vendors | Store API | **The partner's** (white label) |
| `apps/ui/platform` | [platform/](platform/README.md) | `platform.dripfunnel.com` | Partner users | Platform API | DripFunnel |

## 1. Decisions

| Decision | Rejected | Why |
|---|---|---|
| **Static SPAs on Cloudflare Pages**, no server code | Next.js with server routes | A UI deploy can't break the API; the UI is plain static files at the edge (../ARCHITECTURE.md §1). |
| **Vite, React, TanStack Router** (file routes, typed params and search) | Next.js static export | Fast builds, no server features to avoid, typed URLs. |
| **One SPA per audience**, each with its own host and API | One console with role switches | A screen or endpoint for staff can't be reached from a partner or merchant session; each app ships only what its users may see. |
| **Each SPA talks only to `/api` on its own host** | A shared `api.` host | Same origin: `httpOnly` cookies stay first-party, no CORS. |
| **Types come from `apps/api/schema/*.graphql`** | Importing `apps/api` | No server code can reach a browser bundle; lint forbids the import. |
| **`shared/` only for what a second app needs** | Shared components in advance | No speculative abstractions; move code the moment a second app needs it. |

## 2. Folder structure (every SPA)

```
apps/ui/<app>/
  src/
    main.tsx                mount, router, providers; imports @dripfunnel/shared/ui/tokens.css
    routeTree.gen.ts        generated by the router plugin; never edit
    routes/                 TanStack Router file routes; each renders one feature screen
      __root.tsx            the root outlet
      _auth.tsx, _auth/     signed-out screens: sign-in, sign-up, invitation, password reset
      _app.tsx, _app/       signed-in screens; _app.tsx is the shell (nav, context bar)
    features/<area>/        one folder per area: its screens, private components and hooks
    api/<area>.ts           this app's GraphQL operations for that area, typed from the schema
    nav.ts                  the navigation as data, per role (§5)
    messages/               en.json (+ other locales); index.ts exports the active catalogue
    brand/                  (store only) loads the partner's look for the hostname
  index.html  vite.config.ts  tsconfig.json  package.json  README.md
```

- **Routes are thin**: a route file declares the path, params, search schema and loader, and
  renders one screen from `features/`. It never holds layout, logic or text.
- **Features own screens.** `features/products/ProductList.tsx`, `features/products/ProductForm.tsx`.
  Components used by one area stay in that area; used by two areas of the same app, they
  move to `features/common/`; used by two apps, to `shared/`.
- **`api/` is the only place that writes GraphQL.** One file per area, operations named for
  what they do (`productList`, `updateProduct`), using the client from
  `@dripfunnel/shared/graphql`. Screens call these functions, never `fetch`.
- **Named exports only**, one component per file, file named after the component.
- `vite.config.ts` proxies `/api` to the local Worker (`http://localhost:8787`), so local dev
  has the same origin rules as production. Ports: store 5173, platform 5174, admin 5175.

## 3. Talking to the API

- One client per app (`createApiClient()` from `@dripfunnel/shared/graphql`): same-origin
  cookie, a timeout on every call, errors surfaced as `ApiError` with the API's stable code.
- **Handle errors by code, never by message** (`PLAN_LIMIT_REACHED`, `NOT_FOUND`,
  `FORBIDDEN`…). Each code maps to a designed state or a message from `messages/`.
- **The API decides; the UI displays.** Prices, totals, tax, stock, permissions and plan
  limits come from the API. The UI never computes a price or decides whether an action is
  allowed; it hides or disables controls only as a courtesy, the API enforces.
- **The session is an `httpOnly` cookie** the app never reads. The browser holds no token.
  In the merchant portal the acting store travels with each request and the server checks
  it against the session's memberships (docs/api/ACCESS.md §4); the app may remember the
  last store as a convenience only.
- Never display a secret, a full card number, a password or a token, even if an API
  returned one by mistake.

## 4. Text, formatting and look

- **No hard-coded user-facing text.** Every string is in `messages/<locale>.json`, keyed by
  area (`home.title`). Components take words as props.
- **Format with `Intl` through `@dripfunnel/shared/format`**: money (always with its
  currency, from integer minor units), dates in the named time zone, numbers, addresses.
  Never assume a country.
- **Style only with the tokens** in `shared/ui/tokens.css` (`--df-*`). No hard-coded
  colours. The merchant portal overrides the brand tokens with the partner's look before
  anything renders; the two consoles use DripFunnel's. DripFunnel's values come from the
  style guide ([../../designs/design.md](../../designs/design.md) §5–7).
- **Fonts**: Inter for text and Manrope for headings, loaded from Google Fonts by a `<link>` in
  each app's `index.html` (decided 2026-09-29). It is a third-party request on every page
  load; the token font stacks fall back to the system font when it is blocked.
- **Accessibility is WCAG 2.2 AA**: keyboard, screen reader, visible focus, contrast, reduced
  motion. Phone first in the merchant portal; desktop first in the consoles, which must
  still work on a phone for the essentials.

## 5. Navigation and permissions

- **Navigation is data** in `src/nav.ts`: the rows per role, grouped, with each row's path,
  icon, badge source and state. Screens render the app's nav component; they never assemble
  rows themselves.
- **What a role can't use** differs by app, on purpose:
  - **Merchant portal: absent, not disabled.** A greyed row tells a vendor what exists in
    the merchant's store. A vendor opening a URL that isn't theirs sees "not found".
  - **Admin and partner consoles: visible and disabled, with the reason and the role that
    can** ("Finance can issue refunds"), so insiders know whom to ask (CONSOLE-DESIGN §4).
- **Locked** means "not yet" (for example during provisioning); **absent** means "not for
  you".
- **Badges mean work waiting**, never trivia counts.
- Every nav row must resolve to a real screen or an explicit placeholder; a route audit in
  CI clicks every row *(planned)*.

## 6. Designed states

Every screen designs, and can show without a backend, its:

| State | Rule |
|---|---|
| Empty | An explanation and the action that fills it. A new store, partner or platform is empty everywhere, so this is the first impression |
| Loading | Skeletons; never a zero that later becomes real |
| Error / backend unreachable | Plain words first, details behind a click; keep what the user typed |
| Permission denied | Per §5: absent or "not found" in the portal, disabled with reason in the consoles |
| Read-only | Past due (portal), support session (portal), Read-only roles (consoles) |
| Partial / stale | One integration down, data behind: say so, with the time of the last update |
| Confirmation | Destructive actions restate the consequence and name the target |

**Reachable without a backend**: each screen accepts `?state=<name>` in development and
preview builds (`/home?state=empty`, `/sign-in?state=expired`), and lists its states in the
screen file's header comment. The helper lives in `shared/ui` once a second app needs it.

## 7. How to add a screen

1. **Open the screen in its prototype** and click through it: the entry files are listed in
   [../../designs/design.md](../../designs/design.md), which maps every screen to its file,
   and the prototype controls let you reach each state. Check the screen's entries in
   `designs/MISSING-FEATURES.md` and `designs/INCOMPLETE-FEATURES.md` so you don't build a
   dead end. The prototype decides **behaviour**; `docs/` decides **scope and rules**
   ([../README.md](../README.md) §3).
2. Find the flow or part in the app's design document (for example
   [store/DESIGN-BRIEF.md](store/DESIGN-BRIEF.md) flow 21, or
   [admin/CONSOLE-DESIGN.md](admin/CONSOLE-DESIGN.md) part I). If it isn't specified, ask.
3. Check the roles that may see it in the app's guide (and docs/api/ACCESS.md §5).
4. Add the API operations in `src/api/<area>.ts`. If the API lacks a field, add it in
   `apps/api` first (docs/api/README.md §6) and regenerate the schema.
5. Add the screen in `src/features/<area>/`, its words in `messages/`, and every state (§6).
6. Add the route file in `src/routes/_app/...` rendering the screen, and the nav row in
   `src/nav.ts` for the roles that may use it.
7. Reuse from `shared/ui` first; if you write something a second app already has, move it
   to `shared/` in the same change and say so.
8. Tests: unit tests for any logic (formatting, state mapping, nav per role); a Playwright
   journey for key flows *(planned: `test:e2e`)*.
9. Run `pnpm turbo run build typecheck lint test`.

---

## 8. Rules

- No server code, no secrets, no API keys in any SPA.
- No business logic: no price, tax, stock or permission computed in the browser.
- No imports from `apps/api` (lint), and none between SPAs; share only through `shared/`.
- No default exports; no local lint or tsconfig overrides.
- Every console write is audited by the API; the UI asks for the reason where the action
  needs one (suspend, refund, support session).
