# @dripfunnel/storefront-core

## 3.0.0

### Major Changes

- bce8a69: The address form (checkout and My addresses) shows its map with the form, above the fields, when the store has a map key (#1615). There is no "Pin on map" button any more: a search box above the map lists matching places, and a pin dropped, nudged or chosen sets the point and fills Address, City, State and Postal code (and the country, when the shop sells there), never Name, Phone or Apartment. A new address with nothing to go on opens the map where the browser says the shopper is. The fields follow the warehouse form: Name, Address, Apartment, City, State and PIN code, then Country below PIN code, then Phone. Required fields show the `address.requiredMark` (`*`) after the label and carry `aria-required`, and `TextField` takes `required` and `requiredMark`. The map's message keys `address.map.open`, `move`, `confirm`, `cancel`, `close`, `hide`, `finding` and `remove` are gone (the pin can be moved, not cleared); `address.map.search`, `searchPlaceholder`, `suggestions`, `searchNone`, `searchUnavailable` and `unpinned`, and `address.requiredMark`, are new. Major because every live store's address form changes (docs/code/ARCHITECTURE.md §5), so it reaches a store at its merchant's next publish. A theme that styled the old button or its dialog (`.field > button`, `[role=dialog]`) finds those rules matching nothing; the Classic theme's are removed here, and the map draws in core's own look otherwise. No other theme file has to change; its upgrade note is for the release card to add (storefront ARCHITECTURE §7.1).

### Minor Changes

- 1878dba: The link under the code box on Create an account, Sign in and Forgot password follows the store's sign-in setting (#1566): "Use another email" for email only, "Use another number" for a mobile number only, and "Use another email or number" for both. The starting themes' sign-in views pick the text from `useSignIn().ways`, and each ships `shop.account.anotherEmail`. Existing stores get it through the upgrade's codemods in 3.0.0 (a theme that changed the view, or that has other languages, follows the upgrade notes).
- f955491: A line with answers to the product's questions can change quantity and be removed (#1641). Its **+**, **−** and **Remove** were refused by the engine, which finds a version's line without answers unless it is given the line's id, so the cart said "That change didn't go through". `useCart()`'s `setQuantity(versionId, quantity, lineId?)` and `remove(versionId, lineId?)` now send the line's id. A theme that names no line, such as an existing store's cart view, gets it from core when the version has only that one line and it has answers; two lines of one version are told apart only by a `lineId`, so a theme should pass `line.lineId` and key its lines by it, as the starting themes now do. The optimistic change touches only the line named. The starting themes also place **Edit** at the left under the answer, through a new `edit` class, where it sat across the whole column; an existing store gets that only when its theme is updated.
- 12cfc6a: The "Before you add" window no longer adds its own "None" to an optional pick-one question (#1572). Only the merchant's choices show, with none picked at first, so a question with its own "No, thanks" no longer offers two ways of saying no. Once a choice is picked, a "Clear" button (named "Clear: " and the question) goes back to no answer; required and multi-pick questions are unchanged. The message `customise.none` is replaced by `customise.clear` and `customise.clearNamed`; a store that worded `customise.none` in its own catalogue can drop it. No change to the package's API.
- 1deec03: The upgrade brings scroll-loading lists to existing stores (#1570). The release notes gain codemods that rewrite the starting themes' Account › Orders and Blog views, which asked for a "Load more" click, so the next page loads as the end of the list nears the screen, with a "Loading more…" line, a Try again after a failure and the number shown announced, and that turn the "Load more" button of a product grid from before core 0.12.0 into the scroll-loading one. For a theme that changed those views the notes give the migration agent the steps. No change to the package's API: the themes call `useLoadOnScroll` with `useOrders()` and `useBlog()`'s own `loadMore`, `more`, `loadingMore` and `loadMoreFailed`.
- 218d468: A live page shows a thin loading bar at the top while it checks the shop for newer content (#1578). A live page starts from the answers saved at the last Publish and asks the Shop API again, so a change made since (a product's A+ content, a price, a photo) used to appear a moment later with no sign it was coming. `PrefilledProvider` now draws the bar while any pre-filled answer is being asked again, marks the page `aria-busy`, names the bar "Checking for updates" (`refresh.checking`) and stops its animation under reduced motion. It goes away when the newer answers arrive or a check fails, and the page keeps what it shows. The header menu (#1481), the preview, the studio and a question the build had no answer for are unchanged. Core draws it, so every theme and every existing store gets it with the upgrade, with no theme change.
- b421f6c: A shopper's order gives where it is delivered and its courier parcels (#1691). `useOrder()`'s `order` gains `shippingAddress` (null for a pickup or a digital order) and `shipments`: each parcel with a tracking number, as `{ courier, number, url }`, oldest first, with `url` null where the courier gives no tracking page. Both are optional on `Order`, so a theme that builds one needs no change. The starting themes' order view shows each parcel as "{courier} · tracking {number}", the number linked to its tracking page, and ships `shop.order.shipment` and `shop.order.shipmentNoCourier`; an existing store shows it only when its theme is updated.

- 8e098d8: The sign-in, create-account and reset-password pages can draw their form once (#1490). `useSignIn()` now returns `waysKnown`: false from the first draw of a live page until the Shop API has answered which ways the store signs shoppers in by, true after, at once on a preview (which never asks), and when the store can't be asked (`ways` is then email only, so no page waits for ever).   `ways` is unchanged (email only until the answer, both on a preview), so a theme that doesn't read `waysKnown` draws as it always did.   The Classic, Baseline, Beauty, Electronics, Fashion, Grocery, Home and Jewelry themes read it. Market has no sign-in view.

### Minor Changes

- c297994: A theme can now tell that Add to cart is working (#1292). `<AddToCart>` and `<BuyNow>` accept a function as their children, which gets `{ busy }` (true from the press until the engine answers), and their button carries `aria-busy` while busy, so a theme can show "Adding…", for example `<AddToCart versionId={id}>{({ busy }) => (busy ? t('shop.product.adding') : t('shop.product.add'))}</AddToCart>`. This is a minor (docs/code/ARCHITECTURE.md §5): new behaviour, backward-compatible, no theme has to change.

- 2a571fc: `storeCsp` takes a fourth argument, `fonts`, and names Google's font hosts (fonts.googleapis.com and fonts.gstatic.com) only when it is true, so a store whose theme lists no Google font keeps them out of its CSP. - 7f87d08: The validator lets a theme do more of what a designer asks (2026-11-12): words and numbers may be written in the code as well as in content files, while every literal text in the code is now checked for invented prices, stock, urgency, ratings and countdowns exactly as content is; any CSS or motion property may animate (motion's values still written out); more elements and attributes (`label`, `code`, `pre`, `progress`, `meter`, SVG text, masks, clip paths and filters); `lucide-react` icons; Google Fonts listed in `theme.css`'s `@theme { --google-fonts: 'Bebas Neue'; }`, with the CSP letting fonts.googleapis.com and fonts.gstatic.com load; and the page budgets rise to 200 KB of JavaScript and 120 KB of CSS, gzipped. Loading Google Fonts sends each shopper's IP address to Google, so a store that lists fonts may need to disclose it.
- dd3e57b: The Size chart window has a cm | in switch (#1571). It opens in the unit the merchant saved the chart in, and the shopper can switch to the other, both ways. Lengths and ranges convert cm ↔ in (× or ÷ 2.54, rounded to one decimal); a weight column (a name that says weight, kg or lb) converts kg ↔ lb (× or ÷ 2.2046) and its name follows ("Baby weight (kg)" ↔ "Baby weight (lb)"). Sizes, size systems and words stay as typed, the line under the table follows the switch, and switching back gives the merchant's own numbers. The window shows no switch for a chart whose unit isn't `cm` or `in`.
  
  New messages `sizeChart.switch`, `sizeChart.switch.cm` and `sizeChart.switch.in`. This is a minor (docs/code/ARCHITECTURE.md §5): new behaviour inside a core component, backward-compatible, no theme has to change.
- 7f87d08: The studio frame now tells the portal when a section of the theme throws (`df-studio:problem` with the section's name, never the error), so the studio can say the page couldn't show instead of leaving a blank preview. Each catch is posted, a repeat after a hot reload too. Nothing changes on a live or preview site, and no code change is needed in a theme.

- 9273f5b: A product whose version has Track stock off no longer says "In stock" on the live site (#1278): the starting themes (baseline, classic, market) show the stock line only when `useProduct().stock.available` is a number, which core already gives (null for an untracked version). `@dripfunnel/storefront-core` itself does not change; this entry carries the theme edit to stores that already have their own copy of a starting theme.   kind: replace
  paths: ['src/theme/pages/ProductPage.tsx']
